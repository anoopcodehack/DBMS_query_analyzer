Optimizer Diagnostics & Architectural Explanation

1. Access Path Transformation

Without an index, the storage engine reads every disk page in table `DemoRecords` sequentially. With a secondary B-Tree index, it jumps directly to matching keys.

2. Buffer Pool & Disk I/O Impact

Full Table Scans evict active working sets from the InnoDB buffer pool. B-Tree lookups touch only root-to-leaf pages (~3 page reads), dramatically cutting I/O wait times.

3. Mathematical Improvement

Improvement (%) = ((T_before - T_after) / T_before) * 100

Technical Assessment & Viva Voce Guide

Department of Computer Science & Engineering syllabus reference.

1. Third Normal Form (3NF) Compliance

Relations satisfy 1NF (atomic values) and 2NF (surrogate single-column PKs prevent partial functional dependencies). Transitive dependencies are eliminated: `query_name` is stored in `QueryCatalog` rather than repeated across thousands of `BenchmarkResults` records.

2. B-Tree Indexing vs Full Table Scan Complexity

A Full Table Scan requires sequential read of all disk pages (O(N) complexity). An InnoDB B+Tree index structures search keys in balanced nodes of O(log N) complexity, resolving matches via 3 to 4 page reads pointing to clustered primary key leaves.

3. Database Trigger Implementation

Trigger `trg_benchmark_result_audit` executes on `AFTER INSERT` on `BenchmarkResults`. Using pseudorow `NEW`, it captures `result_id` and latency directly in MySQL engine space without application-level overhead.

4. Stored Procedure Architecture

`CALL GetBenchmarkHistory(p_query_id)` executes parameterized multi-table joins on the server, ensuring query plan caching and avoiding repeated network round-trips for reporting.
